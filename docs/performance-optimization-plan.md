# Codex / Cindy 清理性能优化方案

实际收益和测量边界见[性能基线](performance-baseline.md)。

## 目标与基线

让列出记录、准备清理和批量删除都减少重复工作，并在耗时阶段显示进度。
保留精确客户端/物理存储、冻结计划和授权、关闭客户端、漂移阻断、未知结果不重发、
元数据输出及恢复验证规则。全部验证使用临时数据和模拟删除接口。

当前 Windows 临时数据基线：

- 500 条记录的单次 inventory：native 1.440 秒，Cindy 2.177 秒。
- 同一规模中为 1 条记录生成计划：native 2.956 秒，Cindy 6.123 秒。
- 100 条批量计划的 cProfile 结果：native 5.132 秒，Cindy 7.387 秒；
  候选级联合并占约 72%–85%，主要是两两比较时重复解析物理路径。
- 1/10/100 条健康 native 模拟删除中，codex_state 模块分别执行
  10/64/604 次无 WHERE 的 threads 查询；顶层“两次 catalog pass”测试仍然通过。
- 上述为单次本地测量；带 profiler 与不带 profiler 的秒数不可直接比较，
  也不能据此推断真实 Codex API 或用户实际数据库的耗时。

## 优化内容

| 工作 | 用户可见结果 | 验收方式 |
|---|---|---|
| 按存储和记录建立索引，替代候选/重叠的两两比较 | 批量计划随数量增长更平稳 | 1/10/100/更大样本，路径解析次数与范围冲突测试 |
| 合并删除校验中的重复关系读取，定点读取已批准证据 | 批量删除减少数据库往返 | 底层 SQL 计数，以及新关联、漂移、超时和未知结果回归 |
| 对 Windows 短暂文件占用有界重试日志替换 | 减少日志落盘偶发阻断 | 同一临时文件重试、耗尽阻断、不重发删除请求 |
| 显示清理阶段与等待进度，限制宿主进程检查等待 | 长任务可见，宿主检查不会无限挂起 | stdout JSON 兼容、stderr 进度、超时阻断测试 |
| 优化扫描构建中的重复路径/元数据处理 | 列表与计划准备减少重复处理 | native/Cindy inventory 等价、临时规模基准 |

## 实现边界

- 缓存只在具有明确生命周期和失效依据的读取阶段内复用；不做跨操作的永久信任缓存。
- 精确删除仍需证明目标及完整关联范围。不能通过漏扫、减少授权验证或隐藏残留来提速。
- 同批共享 Codex app-server；结果 unknown 仍只进入 status/verify。
- 进度只含阶段、数量、时间及操作标识；自动化 stdout 继续保持原有 JSON 契约。
- 先消除已测出的重复工作。持久化增量索引、全新列表协议及大规模模块拆分，
  只有本轮测量证明仍然必要时再纳入，避免同时改变存储和授权协议。

## 验收与后续

实现采用局部性能重构：库存构建只在当前读取作用域复用已证明的物理路径；
计划按存储、后代及记录别名索引匹配；删除的同一次检查共享关系快照，写入前后
仍分别读取新证据。另补上空 Cindy 原生存储的成功扫描证据，防止删除最后一条后
错误返回 `terminal_scan_incomplete`；缺失、损坏或不支持的数据库仍不能据此宣告完成。

宿主进程检查超时及 `--progress` 改善等待反馈。进度是阶段和动作事件，
不承诺阻塞调用期间按秒刷新。日志替换重试只针对同一已落盘临时文件，
不重建删除请求。最终测量与剩余边界见[性能基线](performance-baseline.md)。

对比相同解释器、相同临时样本、相同命令的优化前后结果；同时记录扫描、计划、
执行含验证的合计耗时，以及底层查询、路径解析、目录枚举次数。实际秒数是观测值，
复杂度和调用次数使用确定性回归检查，避免依赖机器负载的脆弱测试。

任何仍随动作数量增长的全量读取都需说明来源、必要性和后续边界。
