# 清理性能基线

本文件只记录匿名性能数据，不记录 thread ID、聊天正文或用户目录。

## 2026-08-19 基线

- 场景：单一 Codex 物理存储中的 53 个根删除动作。
- 总耗时：901.777 秒。
- 平均耗时：约 17.015 秒/动作。
- 已确认瓶颈：执行前已有一次完整快照，但逐 action guard 又调用完整
  adapter 扫描和完整计划构建，形成 `N × 全库扫描`。

## 重构验收目标

- 默认 planner 对每个 store 只做一次 catalog pass。
- healthy/native 路径已测为计划一次、终验一次两次 full catalog pass。
- 每个 action 只读取与其物理存储、记录身份、活动引用和关联范围有关的证据；action
  loop 不重建完整 catalog/plan/frontend。
- anomaly scanner 可有来源特定读取；两次 full catalog pass 不对所有分类作统一承诺。
  测试直接统计各路径的扫描调用次数。

## 2026-09-10 复测方法

[本轮优化方案](performance-optimization-plan.md)覆盖扫描、计划、执行和等待反馈。
使用仓库自带的 [基准脚本](../tools/benchmark_cleanup.py)，无需第三方依赖：

```powershell
python tools/benchmark_cleanup.py --sizes 10 100 --repeat 1
```

脚本只生成临时 SQLite/JSONL 样本，并注入模拟 Codex 删除服务和客户端检查；
不接受真实记录路径，不调用真实 Codex API。JSONL 输出包括客户端、样本数量、阶段、
耗时、结果状态、删除请求次数和 codex_state 内的 threads 查询次数。
`run` 表示计划、执行及最终验证的合计；`plan_one` 表示从全部样本中选择一条。

比较应使用相同解释器、相同样本和机器负载；必要时增加 `--repeat` 取中位数。
SQL 计数只覆盖 codex_state 模块，不能解释为整个进程全部 SQL 的数量，
更不能把出现 WHERE 当作底层 SQLite 不需要扫描的证明。

确认性能时必须同时检查 `status`：native/Cindy 的 run 都应为 `complete`。
旧版本的 Cindy 空库场景可能返回 `terminal_scan_incomplete`，这应作为结果正确性
问题报告，不能把未完成操作的秒数直接当作成功清理速度。

## 2026-09-10 优化结果

Windows、Python 3.12.10，同一脚本及 100 条健康独立记录，分别运行 3 次，
下表为中位数（秒）。优化前为 `0132a5f`，整合后为 `5179d6f`；命令参数为
`--sizes 100 --repeat 3`，使用默认的两个客户端和四个阶段。测量使用模拟服务，
机器后台负载未受实验室控制，秒数只代表本机观测。

| 客户端 / 阶段 | 优化前 | 优化后 | 结果 |
|---|---:|---:|---|
| Codex 列表 | 0.274 | 0.057 | 两版均完成 |
| Codex 选择 1 条生成计划 | 0.529 | 0.100 | 两版均 ready |
| Codex 全部生成计划 | 4.198 | 0.122 | 两版均 ready |
| Codex 清理全程，含计划与终验 | 12.702 | 6.667 | 两版均 complete |
| Cindy 列表 | 0.405 | 0.064 | 两版均完成 |
| Cindy 选择 1 条生成计划 | 1.067 | 0.170 | 两版均 ready |
| Cindy 全部生成计划 | 5.432 | 0.346 | 两版均 ready |
| Cindy 清理全程，含计划与终验 | 17.593 | 11.745 | 旧版 unknown，新版 complete |

旧版 Cindy 三次都发出 100 次模拟删除，但最后清空原生存储后丢失成功扫描覆盖，
返回 `terminal_scan_incomplete`。新版保留经数据库与扫描结果证明的空存储覆盖，
三次均 complete，因此 Cindy 全程数字不能解读为同等成功结果的速度倍数。
最终版本的 native/Cindy 共 6 次运行均为 complete，每次恰好发出 100 次请求并
只启动 1 次模拟服务。诊断阶段复现过日志原子替换的 Windows `WinError 5`；
本轮为同一已落盘临时文件增加有界替换重试，不重发业务删除。

确定性计数与规模检查：

- 100 条完整运行中，codex_state 内无 WHERE 的 threads 查询由 604 次降至
  204 次；该模块全部 threads 查询由 1105 次降至 705 次。
- 立即写入前和写入后验证仍各做一次新关系读取，完整运行剩余 `2N + 4` 次
  无 WHERE 的 threads 查询。用于发现新后代或边界关系的这些读取仍随动作数增长；
  这不是整库扫描成本已经与批量大小无关的承诺。
- 候选合并、重叠检查和记录选择改为索引匹配。1000 个独立动作/选择器回归
  验证每个动作只提取一次身份；路径缓存仅在一次只读库存构建中共享。
- 核心优化后的 1000 条单次抽查：native/Cindy 列表为 0.467/0.537 秒，
  全量计划为 1.113/3.477 秒；此项用于规模观察，不与较小样本直接计算提速比例。

回归覆盖范围冻结、漂移、未知结果恢复、空库完成判断、
底层读取计数、逐动作进度及日志替换失败。宿主进程超时使用模拟测试；
真实 Codex app-server、实际客户端存储及其磁盘占用耗时未在本轮测量。
如果实用中仍慢，下一步应分别记录真实 API 往返和文件读写耗时，再决定是否需要
持久化增量索引或进一步拆分执行流程。
